# 新合同模板(M22)——GasCan已确认的业务口径，供接手会话直接实现

背景：GasCan 提供了一份《住房租赁合同正式标准模板.docx》(见同目录 `original-template.docx`)，
明确要求**明天(2026-09-21)上线时就要用这份新模板**，不是上线后再升级。这比现在系统里那份
6条正文的简版合同(`apps/server/src/contract-pdf/contract-pdf.template.ts`)详细得多——9条正文+
5个附件。本文档记录逐条确认过的业务决策，接手的人/AI直接照着实现，不用重新问一遍。

`wip-edited-template.docx` 是在原始模板基础上，已经应用了下面"已完成的文本编辑"这部分改动的
半成品文件——**这一步已经做完，但还有几处待确认的占位符没最终定稿**(见下方"仍需确认"部分)，
且还没有转成系统实际使用的 HTML/PDF 模板代码。编辑方法见文末"如何继续编辑docx"。

## 已确认的业务决策(按原模板条款顺序)

1. **收款账户(原合同第二条第2款)**：不强调"线下/线上"两种支付路径的区别，合同只写收款人
   姓名。收款人是 **占秀英**(GasCan的母亲)。已改成："乙方应将租金、押金及其他应付款支付至
   甲方指定的收款人【收款人姓名】。收款人或收款方式如有变更，甲方应及时通知乙方，经双方确认
   后适用变更后的收款方式。"——`收款人姓名`作为一个新的全局配置字段(ContractSettings)，默认值
   "占秀英"。**不需要**采集银行账号/收款码等具体账户信息。

2. **出租权利依据(附件一)**：甲方是"受托管理"身份，不是产权人直接出租。固定文案(已确认)：
   "甲方确认其以受托管理人身份签署本合同，对出租范围具有合法、持续的出租及管理权。"
   ——**不需要**采集产权证编号/授权文件编号/有效期这些字段，直接用固定文案。

3. **出租范围/建筑面积**：不做面积字段(每个房间面积不固定，未来另外做)。出租范围固定为
   "房屋全部"(整间出租，不是分租)。已改成："【房屋坐落】；出租范围：房屋全部"，**已删除**原来
   "建筑面积或使用面积：【面积】平方米"这句。

4. **共同居住人——需要新做一个功能**：【2026-09-20晚GasCan追加修订】身份证必须填写完整号码(15/18位)、手机号必填(下方原文的"证件号后四位+手机可选"作废)。原始背景：现有系统一个租约只有一个主租客，没有同住人概念。
   **需要新增**：
   - 新增数据模型，挂在Lease下：姓名、证件号后四位、联系方式(GasCan原话："在系统里面新建
     的时候可以填写，后续也可以补充修改")。
   - UI：新签租约(NewLease.vue)时可以顺便添加；租约详情页(LeaseDetail.vue)可以随时增删改。
   - **不需要审批流程**，纯备案性质的记录。
   - **关于国家备案要求**：已明确告知GasCan，系统存储这些信息≠自动满足政府的房屋租赁/居住
     登记备案要求，那是他需要另外向当地派出所/房屋租赁管理平台单独办理的行政流程，系统只是
     把数据存好方便他随时调取，不承诺满足任何法规要求。**这一点在功能设计和对外说明里都要
     如实保持，不要在UI文案里暗示"系统已完成备案"之类的表述。**

5. **首期租金/提前支付天数**：
   - 首期租金默认等于月租金，不新增字段。
   - "提前支付天数"**不新增配置字段**，直接复用系统设置页(`Settings.vue`)里已有的
     `reminderPreDays`("提前几天提醒"，当前默认3天，存储在 `data/settings.json`，
     由 `AdminService.loadSettings()` 读取，不是Prisma表)。生成合同PDF时这个数字要从
     `AdminService`读取而不是硬编码。

6. **违约分级**：
   - "欠费补救期限"复用现有的 `ContractSettings.defaultOverdueDays`(逾期容忍天数)，不新增字段。
   - **原模板里独立的"一般违约补救期限"概念(第五条第2款，针对转租/隔断/超员等非欠费违约)
     已删除，改成复用同一个"欠费补救期限"占位符**，即整份合同只有一个"违约补救期限"概念。
   - **原模板第五条第4款"甲方无正当理由提前收回房屋"的违约金条款已整段删除**——GasCan明确
     要求"合同里面不提甲方违约的处理情况"，实际发生这种情况时线下另行协商，不写进合同。

7. **提前退租**：与现有"退租申请"功能(M21自助退租，`leases.service.ts`的
   `createTerminationRequest`/`approveTerminationRequest`)挂钩，不是纯文本条款。
   - 违约金机制：**不用改代码**，现有 `calculateSuggestedPenalty()` 已经是
     `租金 × defaultPenaltyMonths(默认1)`，`approveTerminationRequest`已经是"优先从押金里扣，
     不足补足、多余退还"的逻辑，正好符合GasCan说的"基本上就是扣掉押金"(押金通常等于1个月租金)。
   - 合同文案已改成："乙方应支付相当于【提前退租违约金月数】个月租金的违约金，优先从已付
     保证金中扣除；保证金不足以覆盖违约金的，不足部分由乙方补足；保证金高于违约金的，剩余
     部分退还乙方。"——`提前退租违约金月数`占位符生成时应该填 `defaultPenaltyMonths` 的值。
   - "提前退租通知天数"(比如30天)：**GasCan明确说不用做系统强制拦截**——"系统做提醒义务，
     租客实际能否在30天内就完成退租取决于线下实际情况"。也就是：租客随时可以提交退租申请，
     系统**不校验**`requestedMoveOutDate`距今是否满足这个天数，但**提交页面上应该有一句提醒
     文案**告知"根据合同约定应提前N日通知"。这个UI提醒目前还没做，需要补一个。

8. **逾期占用费**：不做成可配置字段，固定文案(已改)："乙方逾期未交还房屋的，按日租金标准
   支付占用期间费用。"(不是原模板暗示的翻倍处理)。

9. **通知送达渠道(原第八条第1、2款)**：
   - **不要在合同正文里出现"本系统"这种暴露具体软件实现的措辞**——这是GasCan的明确要求，
     合同是法律文件，不应该写实现细节，要用更通用的表述。
   - **不新增采集微信账号/邮箱/送达地址这些字段**——原模板第八条第1款要求专门登记这些，
     已改成直接复用合同里已有的甲方/乙方联系电话字段+签约时核验的微信身份，不用新收集数据：
     "双方确认，甲方联系电话【甲方联系电话】、乙方联系电话【乙方联系电话】及本合同电子签约
     时核验的微信身份，为双方业已确认的有效通知渠道。任何一方变更联系方式的，应及时通知
     对方；未及时告知导致的送达风险由其自行承担。"**这条是我推断出来的简化，还没让GasCan
     明确确认，接手时建议跟他过一遍。**
   - 第八条第2款(通知发送渠道)已改成："催缴、整改、解除、交接、结算等通知可通过电话、当面
     口头告知、短信、微信或电子邮件等方式送达，并应留存通知内容、发送时间、发送对象及送达
     状态。其中电话及当面口头告知即时送达；短信、微信或电子邮件发送至双方确认的联系方式，
     且未收到明确失败或退回提示的，于发送后【电子通知送达小时数】小时视为送达。"——GasCan
     原话确认"消息还会包括线下口头通知与手机通知"，已经按这个加进去了。

10. **房屋及物品交接单(附件三)——工作量最大的一块，需要跟现有"交接记录"功能打通**：
    - GasCan确认：**表格不需要"品牌及型号"列，但需要保留"数量"列**。附件三的表格已经从
      "物品名称/品牌及型号/数量/完好情况"4列改成"物品名称/数量/完好情况"3列(docx里的表格
      已经用脚本改好了，见`wip-edited-template.docx`)。
    - **需要新做**：现有 `HandoverRecord.checklist` 字段(`Json?`，形状是`[{item, condition}]`，
      定义在`apps/server/prisma/schema.prisma`)需要**加一个`quantity`字段**，变成
      `[{item, quantity, condition}]`。这是JSON字段，不需要数据库迁移，只需要改前端表单
      (`LeaseDetail.vue`里`handoverForm.checklist`那部分)和后端DTO/类型定义。
    - **需要新做**：一个"默认物品清单"配置(GasCan确认**全局统一一份**，不分楼栋)，建议存在
      `ContractSettings`里(新增一个`Json?`字段，比如`defaultItemChecklist`，形状是
      `[{item, quantity}]`，初始值可以沿用现有12项设施：空调/冰箱/洗衣机/热水器/燃气灶/
      电视/淋浴器/油烟机/床/桌子/椅子/沙发，quantity默认填1)。"生成电子签约"对话框和
      "新增交接记录"对话框打开时都应该**预填**这个默认清单，房东只需要调整数量/勾掉没有的/
      填完好情况，不用每次从空白开始一项项添加。
    - **需要新做**：合同PDF生成时，附件三的表格应该**直接从这条租约实际的CHECKIN类型
      HandoverRecord里读数据自动填**(物品名称/数量/完好情况)，而不是让房东在生成合同的
      流程里再单独填一遍。水电气表底数直接复用现有`ContractSigningTask`的
      `waterMeterReading`/`electricityMeterReading`/`gasMeterReading`字段(这几个已经在用，
      不用改)。"钥匙及门禁数量"、"房屋现状说明"、"影像存档号"这三个是新字段，**还没跟GasCan
      确认**是否需要做成真实可填字段还是先留空/写"无"——接手时建议问一下，或者先按"留空即可"
      处理，不阻塞主流程。
    - 实现顺序建议：这条依赖"生成电子签约"必须在有CHECKIN交接记录之后才能生成完整合同，
      需要确认业务流程上是不是要求"先做入住交接，再生成电子签约"，还是允许合同先生成、
      交接单数据后补——**这个流程顺序问题还没跟GasCan确认，是接手后第一个要问清楚的点**。

11. **费用结算细则(附件五)**：水费/电费/燃气费/网络物业等计费规则文字，做成`ContractSettings`
    里的全局文本字段(每种费用一个文本框)。**GasCan说要去问他母亲实际的收费方式，还没回复**。
    接手时先看GasCan有没有把这几句话发过来；如果还没有，先留空/写"以实际发生为准"这种占位
    文案，不阻塞其他部分上线，等他给了具体文案后再更新配置。

## 如何继续编辑docx(如果还要接着改文本)

```bash
# 解压
unzip -q original-template.docx -d unpacked/
# 用python3.14(本机默认python3是3.9，skill脚本需要3.10+语法)
/opt/homebrew/bin/python3.14 <docx-skill目录>/scripts/merge_runs.py unpacked/
# 直接编辑 unpacked/word/document.xml 里的 <w:t>...</w:t> 文本，不要重新格式化
# 改完重新打包
cd unpacked && zip -Xr ../edited.docx . && cd ..
# 校验
/opt/homebrew/bin/python3.14 <docx-skill目录>/scripts/office/validate.py edited.docx --original original-template.docx
```
docx skill 完整用法见 Claude Code 的 docx skill 文档，本机路径大致是
`~/Library/Application Support/Claude/local-agent-mode-sessions/skills-plugin/*/skills/docx/`
(具体hash每次可能不同，找不到就重新触发一次docx skill它会告诉你路径)。
