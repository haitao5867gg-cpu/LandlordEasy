# REL-001 — Transaction Safety
Priority P1. Status LOCAL_VERIFIED / MYSQL_INTEGRATION_BLOCKED. Implementation base 68878b6 (includes SEC-001). Acceptance Commander. Coordinate leases.service.ts ownership with SEC-001.

## Scope
Review approveTerminationRequest / approveTransferRequest and nested endLease/create/bill/deposit/room/application writes. Choose explicit Prisma transaction context propagation or reliable persisted compensation; prefer a small atomic DB unit with external actions after commit. Include repair completion + maintenance cost linkage if the same demonstrated partial-write blocker exists, documenting evidence.

## Invariants
Termination approval atomically ends lease, changes room/deposit/bill and marks application resolved, or changes none. Transfer atomically ends old lease, creates intended new lease for the same tenant, updates room occupancy/financial records/application. Duplicate/concurrent approval must produce one result; competing attempts to reserve the same vacant room must not create overlapping active leases.
Provider/QR/message calls cannot be rolled back by Prisma. Do not hold a DB transaction open over network I/O. Persist enough existing workflow state for retry/reconciliation, and surface external failure without duplicating lease/deposit/bill/signature. No microservice/queue redesign.

## Acceptance
Inject failure at each intermediate DB step and assert all-or-nothing state on isolated MySQL. Concurrent approval/rejection, double approval and two applicants for one room tested. Retry after network timeout/failure must not recreate the financial operation; describe ambiguous provider outcome handling. Preserve existing amounts, refund rules, bill engine date semantics, historical data and manual confirmation behavior.
Backend typecheck/full Jest plus isolated DB integration evidence and affected browser flows. No production/dev DB mutation. If isolated MySQL unavailable, integration gate remains BLOCKED, not passed by mocks.

## Local implementation checkpoint — 2026-09-06 UTC

### Design and invariants
- `create`, `endLease`, termination approval/rejection and transfer approval/rejection use interactive Prisma transactions. Small internal helpers receive the transaction client, so nested lease, room, deposit, bill, bill-item, application and signing-task writes share one commit/rollback boundary without changing amounts, dates or refund rules.
- MySQL `SELECT ... FOR UPDATE` locks serialize the application row, lease row and target-room reservation. A repeated approval returns the already-approved result without another settlement; approval versus rejection observes one committed terminal state; competing transfers cannot both observe the same room as vacant after acquiring its row lock.
- Transfer approval creates the new lease and a local contract-signing task inside the database transaction, and persists an approval-supplied ID card when the existing tenant record lacks one. QR creation, PDF generation, WeiQian upload/task creation and customer messaging start only after commit. A post-commit retry reuses the persisted signing task instead of creating another lease, deposit entry or signing task.
- Repair completion and its positive-cost maintenance record use one transaction after locking the repair request. A failed cost-record write rolls back the resolved state, and concurrent completion cannot duplicate the maintenance cost.
- E-sign launch claims `FOLLOWED -> LAUNCHING` with a conditional update before provider I/O. PDF generation failure resets to `FOLLOWED` because no provider call began. Any upload/create error leaves the task in `LAUNCHING`: the remote outcome is ambiguous, so automatic retry is suppressed. The landlord lease detail labels this state `发起结果待核对` and directs the operator to search WeiQian by `LE-{taskId}` before recovery. After provider success, only the local persistence write is retried; final persistence failure logs the non-PII provider bId for manual recovery. `CREATED` is persisted before the supplementary customer-service message, and message failure is treated as best-effort rather than surfacing a false launch failure.
