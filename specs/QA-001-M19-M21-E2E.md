# QA-001 — M19–M21 End-to-End Acceptance
Priority P1 release gate. Status READY AFTER OPS-001 DEV ENV. Owner: QA worker; acceptance: Commander.

## Objective
Prove the existing M19–M21 journeys work end to end on the exact connected dev candidate. This adds no business scope.

## Journey matrix
- Tenant binding: service-account entry/OAuth, identity match, already-bound, wrong phone/name, expired session and retry.
- Contract: preview, follow/bind prerequisite, launch, `LAUNCHING`, provider failure, manual confirmation, tenant/landlord authenticated download and forbidden access.
- Termination: submit, duplicate submit, cancel where supported, landlord approve/reject, settlement/bill/lease state and retry after network failure.
- Transfer: submit, target-room conflict, approve/reject, old/new lease consistency, deposits/bills/signing task and duplicate/concurrent approval.
- Repair: tenant submit with validation/images where supported, landlord processing, completion/cost, failure rollback and tenant-visible status.
- Announcement: landlord target selection, send result/partial failure, tenant receipt/list/empty state and duplicate-action handling.

## Execution rules
Use deterministic non-production fixtures with a manifest and cleanup plan. Record API and UI evidence for each case; never convert fixture-only Playwright into a claim of connected persistence. Run current automated regression first, then manual mobile/WeChat walkthroughs for gaps. Separate mock, sandbox and real-provider evidence.

## Acceptance
No open P0/P1 defect; every required path is PASS or has a Commander-approved non-blocking disposition. Evidence identifies candidate SHA, environment, account roles, case count, failures/retries, screenshots and cleanup result. Update `RELEASE_GATE.md`; defects get linked Issues rather than silent notes.
