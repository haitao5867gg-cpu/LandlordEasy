> 本文档由 Claude Code 设计，Kiro CLI 按此文档实现 Playwright 测试脚本并执行，Claude Code 复核结果、判断优先级并决定是否需要代码修复。

## 0. 执行方式与环境

- **目标环境**:`https://dev.landlordeasy.cn`(不是本地 e2e 沙盒的空种子数据库,用真实历史数据,能测出更真实的场景;不需要起本地 Docker MySQL / 本地 build 后端,避免本机 Node 版本兼容问题)。
- **框架**:复用仓库已有的 `@playwright/test`(1.55.0),新建 `e2e/dev-remote.config.ts`,`baseURL: 'https://dev.landlordeasy.cn'`,`use: { ...devices['Desktop Chrome'], channel: 'chrome' }`(用系统 Chrome,不依赖 Playwright 自带 Chromium 下载,这台机器上载自带 Chromium 之前反复卡死过)。不需要 `webServer` 配置项。
- **登录**:dev 环境 `WECHAT_MODE=mock`,走 `/login?mock_openid=xxx` 或页面里的 mock openid 输入框,不要走真实微信授权。房东测试账号用种子数据里已有的房东(`mock_landlord_001`,对应"张大海"),不要新建房东账号做主账号(除非测试用例本身就是"新增房东")。
- **测试数据隔离原则**:凡是测试过程中新建的数据(房间/租约/维修记录/支出/楼栋/房型等),**名称/备注字段必须带上统一前缀 `E2E_QA_` + 时间戳**,方便测试后识别和清理,不要污染真实历史数据的可读性。房间号类的数字字段用明显不会跟真实房号冲突的高位号段(比如 9xx)。
- **每个测试文件放在** `e2e/tests/landlord-<模块>.spec.ts`,不要全部塞进一个文件,方便单独重跑和定位失败。
- **输出要求**:执行完之后,除了 Playwright 自带的 pass/fail 汇总,请额外产出一份 `e2e/LANDLORD_TEST_REPORT.md`,格式:每条用例一行,状态(✅通过/❌失败/⚠️体验问题) + 简短说明;失败的用例附上失败截图路径(Playwright `screenshot: 'only-on-failure'` 已配置,截图会在 `test-results/` 下,report 里给出相对路径即可)。**不要只写"全部通过"这种笼统结论**,按 COLLABORATION.md 的验收标准,每条用例都要有可核实的具体结果。

## 1. 已知体验问题(前置发现,测试时重点验证是否属实,属实则一并记录严重程度)

以下是代码走查阶段已经发现的疑似体验缺陷,不是凭空猜测的测试点,请在对应模块的用例里专门验证一遍现象是否真实存在,并在报告里注明"确认属实"或"实测后发现不成立"。

| # | 现象 | 涉及页面 | 严重程度(Claude初判,可在报告里给出你的看法) |
|---|------|---------|---------------|
| A | 房间列表用了 `keep-alive`,从房间详情页新签租约/退租后返回列表,列表不重新请求,显示的房间状态是旧的(比如新签后房间应变"已租",但列表还显示"空置") | RoomList.vue | 高——直接误导房东当前房源状态 |
| B | 工作台/报表页用 `Promise.all` 并发拉 4 个接口,只要有 1 个失败,其余 3 个已经成功的数据也不显示,页面看起来像全部加载失败 | Home.vue / Reports.vue | 中 |
| C | 逾期账单页、空置房间页没有点击跳转、没有空状态提示(数据为空时区块直接消失,不会有"暂无数据"文案);到期提醒页有点击跳转+有空状态。三个同类"看板明细页"体验不一致 | Overdue.vue / Vacancy.vue vs Expiring.vue | 中 |

| F | 维修记录新增时"房间"是纯数字 ID 输入框,不是房间选择器,房东要自己知道房间数字 ID 才能填 | Maintenance.vue | 中——普通用户基本不可能知道房间ID |
| G | 房东白名单页禁用一个账号后,没有"重新启用"的按钮入口(后端接口其实支持) | settings/Landlords.vue | 低 |
| H | 部分设置类页面(Settings/Landlords/RoomTypes/Buildings)完全没有 loading 状态展示,弱网下会有明显的"卡顿感" | 见上 | 低 |
