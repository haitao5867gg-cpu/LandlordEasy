# 历史数据导入(2026-08,完整历史重建)

> 由 Claude Code 清洗自 GasCan 提供的两份手工记账表(鸿翼/嘉定公寓 + 明远公寓,微信文件名分别是"鸿翼公寓租金耗材(1).xls"和"明远公寓租金耗材.xls")。原始 Excel 结构不规整(每月一个"租金"sheet + 一个"耗材"sheet,列名/列序在不同年份有变化,夹杂手写汇总/备注文字),已用 Python(pandas)脚本清洗成结构化 CSV,过程见本次会话记录。

**这批数据取代 `data/import/` 根目录下旧的 `leases.csv`/`rooms.csv`/`buildings.csv`(那批是早期只做"当前快照"、且租客姓名/电话从未补全的半成品,现在被这批完整历史数据取代)。`expenses.csv` 也一并被这里的 `expenses_clean.csv` 取代(数据源相同,这次重新从 Excel 清洗更完整)。**

## 覆盖范围

- **嘉定公寓**(Excel/微信文件名"鸿翼公寓"):Q/R/S 三栋楼,133 个房号,租金记录 2024-11 ~ 2026-07(部分房间更早的月份数据不完整,因为该物业是逐步扩建/招租的,早期月份入住房间少属正常)
- **明远公寓**:一栋楼,52 个房号(201~218, 301~334),租金记录 2024-01 ~ 2026-07
- 两处物业租金和耗材(支出)记录均逐月覆盖

## ⚠️ 已知缺口(导入前必须知道)

- **完全没有租客姓名和手机号**——原始表从未记录这两项,已跟 GasCan 确认这次先不补,租约记录里这两个字段先留空/占位。这意味着这批房间的租客暂时**无法使用租客端 H5**(登录需要手机号绑定),只影响房东端的运营记录,不阻塞房东端使用。
- 极少数行(3 条)原始"截止日期"数据本身有错误无法解析,已按"起租日+1个月"估算,并在 `remark` 字段里标注了 `[数据清洗:...]`,方便日后核查。
- 原始表里不少行有年份手误(比如"交租日期 2025-12-08,截止日期 2025-01-18"这种,应为 2026-01-18),已按"截止日期应晚于起租日期约1个月"的规则自动修正(取截止日期年份+1),没有再额外标注,如果后续报表数字对不上,可以回头查这个假设是否在个别行出错。
- 房间清单是从租金表里出现过的房号反推的——**如果某个房间从 2024 年到现在从来没有产生过租金记录(比如长期空置、从未招租过),不会出现在这批数据里**,不会被自动建出来。

### `rent_events_no_period.csv`(376 行,没有账期数据的"事件"行)

这些行大多是"退房"标记(该月该房间没有产生账单,因为空置)或者内部备注(比如"鸿翼员工XX日期开始入住"这种员工占用记录,不是对外收租)。有 `deposit_refund` 值的行代表一次押金退款事件,即使没有账期也值得记录。**不建议为这些行生成 Bill,但值得考虑用来辅助判断租约结束时间点、或者生成 DepositRecord 退款记录。**

### `expenses_clean.csv`(896 行,耗材/支出记录)

列:`date`(日期)/`name`(名称)/`unit_price`(单价,多数场景下等同金额,极少数行是"单价×数量"的单价)/`purpose`(用途说明,常包含房号如"R202换水龙头")/`amount`(实际金额,导入时应以这列为准,不要用 unit_price)/`sheet`/`property`。跟系统现成的 `importExpenses()` 期望的字段(date/category/name/amount/remark/buildingName/roomNo)基本能对上,`category` 原始数据没有,需要按 `name`/`purpose` 关键词简单分类(比如"工资"→人工,"网费"/"垃圾费"→固定支出,其余→耗材维修),`roomNo` 可以尝试从 `purpose` 里用房号正则提取(能提取到的可以关联到具体房间的支出历史)。

## 建议的导入设计(租约切分逻辑)

系统的 `Bill` 必须挂在某个 `Lease` 下面,而原始数据是"每房间每月一行"的流水,不是现成的租约区间,需要做"同一房间连续多月记录 → 归并成一个 Lease、Lease 内每月生成一张 Bill"这一步。判断"什么时候算换了一任新租客、该开始一个新 Lease"建议用下面几个信号(任一命中即视为新 Lease 开始):

1. `remark` 包含关键词:`转租`、`新签`、`退房`、`到期退`、`前客户`、`调房`(调房可能是同一租客换房间,也可能是换租客,建议按新 Lease 处理,更保守安全)
2. `new_deposit` 和 `deposit_refund` **同时**在同一行有值(典型的"旧租客退押、新租客交押"模式)
3. 与上一条记录相比,`period_start` 和上一条的 `period_end` 对不上(有明显日期缺口,间隔超过~10天),可能中间空置过一段时间再重新招租
4. 押金金额发生较大变化(不是简单的续租减免几十上百的那种小额调整)

每个 Lease 内部,把归入这个区间的每一行按 `period_start` 排序生成一张 `Bill`(`periodStart`/`periodEnd`/`amount=rent`),因为这些都是历史上**已经收到**的租金记录,`Bill.status` 和对应 `Payment` 都应该标记为已支付,不是待支付状态。`parking_fee`/`commission` 有值时可以作为 `BillItem` 挂在对应月份账单下。

**这个切分逻辑本质上是启发式的,原始数据里换租客的记录方式并不统一(有的写"转租"、有的只是押金变了没写清楚、有的什么信号都没留),不可能保证 100% 判断正确。建议实现时把"命中了哪条信号"记录下来(比如写进 Lease 的备注,或者单独输出一份"低置信度切分点"清单),方便事后人工抽查,而不是假装这个算法绝对准确。**

## 楼栋/房型建议

- 嘉定公寓建 3 栋楼(Q栋/R栋/S栋),房号前缀对应楼栋,楼层可以从房号第二位数字推断(Q1xx=1楼,Q2xx=2楼,以此类推,这个逻辑项目里 `RoomsModule` 批量建房已经有现成实现,复用即可)
- 明远公寓建 1 栋楼,房号 2xx=2楼、3xx=3楼
- 房型不需要精细划分,每栋楼建一个通用房型即可,每个房间的真实租金用 `Room.rentOverride` 字段承载(schema 里已经有这个字段),不需要强行把 133+52 个房间按租金归类出一堆房型
